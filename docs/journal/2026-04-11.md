Settings: production branch `main`, framework preset **None**, build command `pnpm build`, output dir `dist`, env var `NODE_VERSION=22`. pnpm 9.12.0 was picked up automatically from the `packageManager` field — no `PNPM_VERSION` fallback needed.

- Attached `dhfrost.com` (apex) and `www.dhfrost.com` as custom domains on the Pages project. Zone is already in this Cloudflare account, so both were one-click — Cloudflare auto-created the CNAME-flattened apex record and the `www` CNAME → `dhfrost.pages.dev`. SSL provisioned in <1 min.
- Added a zone-level Redirect Rule named `www to apex`: when `Hostname equals www.dhfrost.com`, dynamic 301 to `concat("https://dhfrost.com", http.request.uri.path)` with query string preserved.

**Changes (repo, this commit-set on `chore/cloudflare-deploy-notes`):**

- `docs/journal/2026-04-11.md` — this entry.

**Problems:**
- After attaching `www.dhfrost.com`, `curl -sI https://www.dhfrost.com/` returned empty with `Could not resolve host: www.dhfrost.com`, while `dig +short www.dhfrost.com` correctly returned the Cloudflare anycast IPs (`172.67.196.93`, `104.21.21.37`). Local macOS DNS cache had a stale `NXDOMAIN` from before the record existed. `dig` queries a public resolver directly so it bypasses the cache; `curl` goes through the system resolver and hit the cached negative.

**Resolution:** Confirmed the deploy was actually working by re-running `curl` with `--resolve www.dhfrost.com:443:172.67.196.93` to bypass the system resolver — got HTTP/2 200 with a valid cert, no `--insecure` needed. The cache will clear on its own; documented `sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder` as the manual flush. After deploying the redirect rule, end-to-end verification: `https://www.dhfrost.com/` → 301 with `location: https://dhfrost.com/`, and `https://www.dhfrost.com/writing/foo?x=1` → 301 with `location: https://dhfrost.com/writing/foo?x=1` (path *and* query preserved by the dynamic expression). Apex still 200.
